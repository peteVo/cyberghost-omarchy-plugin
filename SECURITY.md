# Security review notes

## Scope and evidence

The reviewed CyberGhost 1.5.0 Ubuntu 22.04 archive matches SHA-256 `c7cfd8e685f497ecc957636913bc32f8fa55b6ac0bbf19b2a4ebe64d188d03a6`. Its bundled README, changelog, and scripts were reviewed; the executable and certificate/key contents were not printed or extracted as source. The included `client.key` is a PEM private key. The corrected package installs it mode 0600. Keep CyberGhost authentication in the official client and do not expose or reuse vendor secrets.

The original recipe also fetched a Sectigo certificate over HTTP (SHA-256 `72a34ac2b424aed3f6b0b04755b88cc027dccc806fddb22b4cd7c47773973ec0`), although it was unused by `package()`. The corrected recipe removes that unused source. Its package patch is pinned at SHA-256 `52f8f47f1a14ee2c8caebcd5ffa38dffeaa6b44f3b1dfd38f04874753a1c6c74`; the local x86_64 package built successfully with `makepkg --nodeps` but was not installed. Missing dependencies mean that build result does not establish runtime integration.

The vendor executable is x86_64 ELF and requires libc, libdl, libpthread, libz, and GLIBC up to 2.14. In a synthetic isolated HOME/USER invocation it reached the expected missing `/home/cg-review/.cyberghost/config.ini` before help output; this rules out an immediate glibc loader failure in that environment, but does not establish a working authenticated client. No authentication, setup, or live VPN connection was performed. The README documents listing and selecting countries, cities, and specific servers through `--server`; do not guess server names. The package correctly uses `arch=(x86_64)` and `!strip` for the bundled executable.

Do not run the vendor installer, uninstaller, or completion generator. The installer installs dependencies, removes/replaces `/usr/local/cyberghost`, applies mode 755 recursively (which would make the private key readable), runs setup, and generates completions. The uninstaller may remove application/configuration files, and the completion generator executes the vendor binary and writes system completion files. The package recipe stages only selected files and does not run these scripts.

## Resolver and connection claims

The review host has systemd 262.1 and OpenVPN 2.7.8. Pacman metadata confirms `systemd-resolvconf` 262.1-1 provides `resolvconf`, matching installed systemd; `openresolv` and `wireguard-tools` were absent. The corrected recipe depends on `systemd-resolvconf`. The reviewed hook uses `resolvectl` when `systemd-resolved` is active; the package patch refuses to rewrite `resolv.conf` if it is not, and propagates DNS setup/revert errors. No manual symlink or resolver-service replacement is needed. Runtime DNS behavior still requires testing on the target, and this review does not establish DNS/IPv6 protection or a kill switch.

The bridge activates the existing NetworkManager OpenVPN profile named `cyberghost` without reading or storing its secrets. Its official-CLI path checks the installed executable's location and ownership before use. Its explicit `ip` action makes an IPv4 HTTPS request to `api.ipify.org` only while connected and checks connection state again afterward; this discloses the public IPv4 address to that service and does not verify IPv6 routing or DNS behavior. The bridge also does not treat a successful connect command alone as proof of a verified location. These are source-level observations, not runtime security guarantees. CLI output remains untrusted; no raw output or credentials should be logged.

## Validation stages

1. Review the corrected PKGBUILD, patch, package file list, and scriptlets. The archive checksum and bundled scripts have been reviewed; the executable has not been reverse engineered. Confirm package ownership and modes before installation, especially `client.key` at 0600.
2. After explicit approval, installation may be tested on this ThinkPad after backing up relevant configuration. Keep authentication in CyberGhost's official client. Preserve the existing OpenVPN fallback profile (renamed `cyberghost` per the user's request) and do not mutate unrelated VPN profiles.
3. Test service state, route selection, DNS, and IPv4/IPv6 behavior on real hardware, first disconnected and then connected. For a DE-to-NL test, use locations and servers reported by the official client and record the selected profile/location, `ip -4 route`, `ip -6 route`, and `resolvectl status`. Public IPv4 lookup is opt-in: use the bridge's explicit `ip` action or another reviewed method, knowing that the endpoint receives the address. The baseline script itself never makes this request. Treat any apparent DNS or IPv6 protection as unverified until leak behavior is checked independently. Do not claim a kill switch unless its failure behavior is tested.

`tools/host-baseline.sh` is an optional read-only local snapshot for those tests. Its output can contain usernames, interface and device names, local/public IP addresses, and VPN profile names. Keep it local and do not commit or post it without reviewing and redacting it.

## Polkit account identity

An isolated execution with synthetic `USER=root` and `PKEXEC_UID=1000` showed the vendor CLI looking for `/home/root/.cyberghost/config.ini`. It does not derive the invoking account from Polkit's UID. Direct `pkexec cyberghostvpn` is therefore unsuitable for a subscription configured through ordinary `sudo --setup`.

Package 1.5.0-3 adds a small root-owned `/usr/local/cyberghost/omarchy-bridge` adapter. Python isolated mode ignores user Python environment/site paths. It permits only fixed country/city connect arguments or `--stop`, validates a non-root Polkit UID through the system passwd database, supplies a minimal environment with the derived `SUDO_USER`, and executes only the fixed vendor binary. It handles no credentials and installs no daemon or Polkit rule. The unprivileged bridge checks root ownership, write mode bits and effective write access on executables and every parent directory. Unit tests mock privilege and exec; actual Polkit prompts and authenticated CLI operations still require live validation. The user confirmed that official `--setup` and unprivileged `--help` succeeded; no credentials or configuration were collected.

The system package was confirmed installed as 1.5.0-3 together with WireGuard tools and systemd-resolvconf. The session's filesystem remaps root ownership to UID 65534; runtime checks correctly reject that view. Do not alter the production trust checks to accept it.

## Observed WireGuard behavior

A user-run Germany/Frankfurt connection produced a `cyberghost` WireGuard interface, an IPv4 route through it, a successful public IPv4 lookup, and per-link DNS with `~.`. The CLI's own `--status` incorrectly reported no VPN connections. The bridge uses kernel interface/route observations for that known tunnel and permits it through the operation conflict guard while retaining rejection of other VPNs. That observation is not a cryptographic handshake check. IPv6 routes present in the baseline disappeared during this test; cause and restoration are unverified. No Netherlands transition or disconnect-recovery test is claimed. Detailed evidence stays private in ignored `build/` files.

The WireGuard name is a convention, not cryptographic provider ownership. The bridge additionally requires NetworkManager's `NM_ACTIVATION_STATE_FLAG_EXTERNAL` before attributing/controlling that device, rejecting a managed NetworkManager WireGuard profile even if it uses the same name. An unrelated externally created WireGuard tunnel with this exact interface name remains indistinguishable without provider/peer evidence. Do not run such a tunnel alongside this client; the vendor itself reserves that interface name and its stop operation is broad. This guard is not a global VPN ownership detector.
